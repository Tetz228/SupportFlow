# Модули и правила зависимостей

## Текущая схема

```text
SupportFlow.IntegrationTests
            |
            v
      SupportFlow.Api
        /     |      \
       v      v       v
 Identity Organizations Tickets
```

`SupportFlow.Api` запускает приложение и собирает его из модулей. Интеграционные тесты взаимодействуют с системой через API и не подключают модули напрямую.

## Ответственность проектов

### `SupportFlow.Api`

- запуск ASP.NET Core host;
- сборка dependency injection container;
- подключение модулей;
- общие элементы HTTP pipeline;
- конфигурация приложения и health endpoints.

API не должен содержать бизнес-правила предметных областей.

### `SupportFlow.Modules.Identity`

- пользователи;
- учётные данные и аутентификация;
- выдача идентификатора текущего пользователя.

### `SupportFlow.Modules.Organizations`

- организации;
- участники организаций;
- роли и членство пользователей.

### `SupportFlow.Modules.Tickets`

- обращения;
- назначение исполнителя;
- приоритеты и статусы;
- комментарии и история изменений.

## Правила зависимостей

1. API может ссылаться на модули, потому что является composition root.
2. Модуль не может ссылаться на API.
3. Модуль не получает прямой доступ к внутренним типам, `DbContext` или EF-сущностям другого модуля.
4. Прямая ссылка одного модуля на реализацию другого запрещена.
5. Межмодульные контракты должны быть минимальными и отражать бизнес-сценарий, а не удобство повторного использования кода.
6. Общий проект с моделями не создаётся заранее. Shared Kernel допускается только для небольшого набора действительно общих стабильных примитивов.
7. Новое направление зависимости должно быть осознанным архитектурным решением и покрываться тестом, если правило можно проверить автоматически.

## Организация кода внутри модуля

Код будет группироваться по пользовательским сценариям, а не по техническим типам:

```text
Tickets/
├── CreateTicket/
├── GetTicket/
├── SearchTickets/
├── AssignTicket/
├── ChangeTicketStatus/
└── AddComment/
```

Каждый сценарий может содержать собственные endpoint, request/response contracts, validation и handler. Доменные сущности и инфраструктура выделяются тогда, когда для них появляется реальная ответственность.

## Владение данными

На текущем этапе модули используют одну физическую базу PostgreSQL, но не общую модель EF Core:

- каждый модуль владеет собственным `DbContext`;
- `DbContext` является внутренней деталью модуля и объявляется как `internal`;
- каждому модулю выделяется отдельная схема PostgreSQL;
- конфигурации сущностей и миграции хранятся в проекте модуля;
- API читает строку подключения и передаёт её публичной точке регистрации модуля;
- модуль не получает `IConfiguration` и не знает, где хранится секрет;
- другой модуль не может обращаться к чужому `DbContext`, таблицам или EF-сущностям напрямую.

Первым подключён модуль `Organizations`: его `OrganizationsDbContext` владеет схемой `organizations`. Остальные модули получат собственные контексты и схемы при появлении первой сохраняемой бизнес-модели.

EF Core уже реализует паттерны Unit of Work и Repository через `DbContext` и `DbSet`. Универсальный `GenericRepository<T>` не вводится без конкретной задачи, которую нельзя выразить непосредственно через EF Core.
