# Формат ошибок API

SupportFlow использует стандарт Problem Details для машиночитаемого описания HTTP-ошибок. Клиент может опираться на общую структуру ответа вместо разбора произвольного текста.

## Общие поля

- `type` — идентификатор типа проблемы, обычно URI с описанием соответствующего HTTP-статуса;
- `title` — краткое человекочитаемое название проблемы;
- `status` — HTTP-статус, продублированный в теле ответа;
- `detail` — дополнительные сведения о конкретной ошибке, если их безопасно сообщать клиенту;
- `instance` — идентификатор конкретного случая или путь запроса, если он задан приложением;
- дополнительные поля зависят от типа ошибки.

Необязательные поля не гарантируются и могут отсутствовать в JSON.

## Неизвестный маршрут

Если запрошенный маршрут не существует, API возвращает:

```http
HTTP/1.1 404 Not Found
Content-Type: application/problem+json
```

```json
{
  "type": "<URI типа ошибки>",
  "title": "Not Found",
  "status": 404
}
```

Ответ формируется общим `IProblemDetailsService` через Status Code Pages middleware, поскольку routing устанавливает статус `404`, но не создаёт собственное тело.

## Ошибка валидации

Ошибка входного контракта возвращает специализированный Validation Problem Details. Помимо общих полей он содержит словарь `errors`, сгруппированный по полям запроса.

```http
HTTP/1.1 400 Bad Request
Content-Type: application/problem+json
```

```json
{
  "type": "<URI типа ошибки>",
  "title": "One or more validation errors occurred.",
  "status": 400,
  "errors": {
    "Name": [
      "Название организации обязательно."
    ]
  }
}
```

Status Code Pages не заменяет этот ответ, поскольку endpoint уже записывает собственное тело через `ValidationProblem`.

## Неожиданная серверная ошибка

Необработанное исключение преобразуется в безопасный Problem Details с кодом `500`:

```http
HTTP/1.1 500 Internal Server Error
Content-Type: application/problem+json
```

```json
{
  "type": "<URI типа ошибки>",
  "title": "An error occurred while processing your request.",
  "status": 500
}
```

Exception Handler Middleware располагается в начале HTTP-конвейера, до компонентов и endpoint’ов, исключения которых он должен перехватывать. Зарегистрированный `IProblemDetailsService` формирует ответ, а внутренние сообщения исключений, stack trace и сведения об инфраструктуре клиенту не передаются.

Это резервная защита от непредвиденных сбоев, а не замена ожидаемым ответам. Ошибки валидации, отсутствие ресурса и бизнес-конфликты должны явно преобразовываться в соответствующие коды `400`, `404` и `409`, а не маскироваться под `500`.

## Заголовок Accept

Для получения JSON-контракта клиенту следует отправлять один из поддерживаемых заголовков, например:

```http
Accept: application/problem+json
```

## Текущие ограничения

- идентификатор запроса ещё не добавляется в каждый ошибочный ответ;
- ошибки отсутствующих бизнес-ресурсов и конфликтов будут определены при появлении соответствующих сценариев.

Эти ограничения будут устранены следующими шагами общего HTTP-контура.
