# ADR-0003: Разрешить интеграционным тестам доступ к внутреннему контексту модуля

- Статус: принято
- Дата: 2026-09-05

## Контекст

Интеграционные тесты создания организации должны подготавливать схему временной PostgreSQL и проверять сохранённые данные. `OrganizationsDbContext` остаётся внутренней деталью модуля согласно ADR-0002. Первоначальная схема зависимостей разрешала интеграционным тестам ссылаться только на API.

Теперь тестовой инфраструктуре нужен доступ к контексту. Прикладной сценарий при этом должен проходить через HTTP, чтобы проверялись маршрутизация, преобразование JSON, DI, валидация и ответ endpoint.

## Решение

- Добавить явный `ProjectReference` из `SupportFlow.IntegrationTests` в `SupportFlow.Modules.Organizations`.
- Разрешить сборке `SupportFlow.IntegrationTests` доступ к внутренним типам Organizations через `InternalsVisibleTo`.
- Использовать этот доступ для подготовки базы и проверки результатов сохранения. Прикладные действия выполнять HTTP-запросами, без прямого вызова endpoint или его обработчика.
- Получать контекст из отдельного DI scope тестового API. Это позволяет использовать регистрацию модуля, включая провайдер PostgreSQL и отдельную таблицу истории миграций.
- При подготовке тестовой базы вызывать `MigrateAsync` через `SupportFlowApiFactory`. Само предоставление доступа к внутреннему контексту миграции не запускает.

Решение дополняет ADR-0002 для тестовой инфраструктуры. Другим production-модулям доступ к контексту не предоставляется.

## Альтернативы и компромиссы

- Подготовка базы внешним SQL-скриптом или migration bundle сохраняет более строгую изоляцию HTTP-тестов от реализации модуля. Она требует отдельного механизма сборки и запуска артефактов; этот подход рассмотрим при настройке развёртывания.
- Самостоятельное создание `DbContext` в тестах потребовало бы повторять настройки модуля, включая историю миграций. Получение контекста из DI уменьшает риск расхождения тестовой и рабочей конфигурации.
- Объявление контекста `public` расширило бы контракт модуля для всех потребителей. Доступ предоставляем конкретной тестовой сборке.

## Последствия

- Тесты смогут проверять реальные миграции и сохранённые данные, сохраняя HTTP как вход для бизнес-сценариев.
- Тестовая инфраструктура будет зависеть от внутренних типов хранения данных; изменения этих типов могут потребовать обновления тестов.
- `InternalsVisibleTo` открывает все внутренние типы сборки. Ограничение на цель их использования обеспечивается ревью, а не самим атрибутом.
- Пока HTTP-тесты используют внутренние EF-типы для проверки данных, они не являются полностью изолированными тестами системы как чёрного ящика.
