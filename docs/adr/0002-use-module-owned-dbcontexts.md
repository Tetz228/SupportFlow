# ADR-0002: Разделить владение данными по модулям

- Статус: принято
- Дата: 2026-08-19

## Контекст

SupportFlow разрабатывается как модульный монолит с модулями `Identity`, `Organizations` и `Tickets`. Всем модулям на начальном этапе достаточно одного экземпляра PostgreSQL, но общий `DbContext` и общая EF-модель сделали бы границы данных неявными. Любой модуль смог бы обращаться к таблицам и сущностям другого модуля напрямую.

Отдельная физическая база для каждого модуля усилила бы изоляцию, но усложнила бы локальную разработку, транзакции, резервное копирование и развёртывание до появления соответствующих требований.

## Решение

Использовать одну физическую базу PostgreSQL и разделить владение данными на уровне EF Core и схем базы:

- каждый модуль создаёт собственный `DbContext`;
- контекст объявляется как `internal` и не входит в публичный контракт модуля;
- каждый модуль владеет отдельной схемой PostgreSQL;
- сущности, конфигурации и миграции размещаются в проекте владеющего модуля;
- `SupportFlow.Api` читает строку подключения и передаёт её методу регистрации модуля;
- модули не получают прямой доступ к контекстам, таблицам и EF-сущностям друг друга;
- межмодульное взаимодействие выполняется через явные контракты или события.

Первой реализацией решения является `OrganizationsDbContext` со схемой `organizations`.

## Рассмотренные альтернативы

### Один общий `SupportFlowDbContext`

Общий контекст проще настроить, но он объединяет модели всех предметных областей и позволяет создавать неявные связи между модулями. Со временем такой контекст становится общей точкой связанности. Вариант отклонён.

### Отдельная физическая база для каждого модуля

Этот вариант обеспечивает более сильную изоляцию и упрощает будущее выделение сервисов, но требует нескольких подключений, отдельных миграций окружения и решения задач согласованности между базами. Для текущего масштаба затраты не оправданы. Вариант отложен до появления подтверждённой потребности.

### Универсальный репозиторий поверх EF Core

`DbContext` и `DbSet` уже предоставляют Unit of Work и Repository. Универсальная обёртка скрыла бы возможности LINQ и EF Core, добавила бы дублирующий API и затруднила бы сложные запросы. Вариант отклонён; специализированные абстракции допускаются только при наличии конкретного сценария.

## Последствия

### Положительные

- владение таблицами и моделями остаётся явным;
- изменения одного модуля меньше влияют на остальные;
- миграции можно создавать и проверять отдельно для каждого контекста;
- сохраняется простой локальный запуск с одним PostgreSQL;
- модуль проще выделить в отдельный сервис, если это станет необходимо.

### Отрицательные

- для каждого модуля требуется отдельная регистрация и набор миграций;
- межмодульные связи нельзя моделировать обычными navigation properties;
- одна физическая база не обеспечивает изоляцию отказов и прав доступа на уровне отдельного сервера;
- согласованность между модулями требует явных контрактов и архитектурной дисциплины.

## Условия пересмотра

Решение следует пересмотреть, если модулю потребуется независимое развёртывание, отдельное масштабирование, собственный жизненный цикл базы или более строгая операционная изоляция.
