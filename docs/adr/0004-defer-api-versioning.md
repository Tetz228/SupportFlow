# ADR-0004: Отложить явное версионирование HTTP API

- Статус: принято
- Дата: 2026-09-16

## Контекст

SupportFlow пока имеет один HTTP endpoint и не имеет независимо обновляемых внешних клиентов. API и будущий web-клиент разрабатываются в одном продукте, поэтому совместимые изменения можно выпускать согласованно.

Явное версионирование полезно, когда несколько несовместимых контрактов должны существовать одновременно. Добавление версии заранее потребовало бы выбрать способ передачи версии, настроить маршрутизацию и OpenAPI, определить поведение версии по умолчанию и политику прекращения поддержки. Сейчас эти затраты не решают проявившуюся проблему.

При этом отсутствие номера версии не разрешает произвольно менять контракт. Переименование или удаление поля, изменение его типа либо бизнес-смысла, изменение маршрута и несовместимое изменение кодов ответа способны нарушить работу существующего клиента.

Путь `/openapi/v1.json` не означает, что HTTP API уже имеет версию 1. `v1` является именем генерируемого OpenAPI-документа. Текущие прикладные маршруты остаются неверсионированными, например `/api/organizations`.

## Решение

Не вводить явную версию HTTP API на текущем этапе:

- не добавлять сегмент версии в маршруты;
- не передавать версию через query string, заголовок или media type;
- не подключать библиотеку API versioning без сценария одновременной поддержки несовместимых контрактов;
- развивать существующий контракт обратно совместимыми изменениями;
- рассматривать изменение не только структуры, но и смысла существующих данных как потенциальное breaking change;
- принимать решение о механизме версионирования отдельно при появлении подтверждённой необходимости.

К обратно совместимым изменениям обычно относятся добавление необязательного поля ответа и нового необязательного параметра запроса при сохранении прежнего поведения без них.

К breaking changes относятся удаление или переименование существующего поля, изменение его типа или обязательности, несовместимое изменение маршрута, а также изменение бизнес-смысла существующего значения. Конкретное изменение всё равно оценивается с учётом поведения реальных клиентов.

## Рассмотренные альтернативы

### Версия в URL с первого endpoint

Маршруты вида `/api/v1/organizations` делают выбранную версию заметной в запросах, логах и ручных проверках. Подход прост для клиентов и маршрутизаторов.

Он отклонён на текущем этапе, потому что номер появился бы без второй версии и без требования поддерживать старый контракт. Версия в URL также меняет адрес ресурса и может поощрять создание новой версии всего API вместо точечного управления несовместимым изменением.

Если в будущем понадобится наиболее явный и простой для внешних клиентов механизм, URL-сегмент будет рассмотрен первым, но не считается выбранным заранее.

### Версия в заголовке или media type

Такой подход сохраняет стабильный URL и позволяет выбирать представление через metadata запроса. При этом версия хуже видна при ручной диагностике, требует дополнительной настройки клиентов, gateway, кэширования и документации. Media type versioning дополнительно усложняет content negotiation.

Вариант отложен до появления требований, для которых сохранение одного URL важнее простоты использования.

### Версия в query string

Параметр вида `?api-version=1` легко добавить и проверить, не изменяя основной путь. Однако версия становится похожей на обычный фильтр, может быть пропущена в правилах кэширования и хуже выражает выбор отдельного контракта. Вариант отклонён как стратегия по умолчанию.

## Последствия

### Положительные

- маршруты и OpenAPI не усложняются до появления реальной необходимости;
- проект не получает новую зависимость и конфигурацию без пользовательской ценности;
- внимание сосредоточено на обратной совместимости, а не только на номере версии;
- будущий механизм можно выбрать на основании типов клиентов и требований к миграции.

### Отрицательные

- команда должна анализировать каждое изменение публичного контракта на совместимость;
- первый неизбежный breaking change потребует отдельной миграционной стратегии;
- без дисциплины можно незаметно изменить поведение существующего клиента;
- при появлении внешних клиентов потребуется определить срок поддержки и прекращения старых версий.

## Условия пересмотра

Решение следует пересмотреть, если выполняется хотя бы одно условие:

- требуется breaking change, которое нельзя заменить обратно совместимым развитием контракта;
- существующие клиенты нельзя обновить одновременно с сервером;
- старый и новый контракты должны поддерживаться параллельно;
- появляются внешние интеграции или договорные сроки поддержки API;
- требуется формальная политика deprecation и sunset.

При пересмотре необходимо отдельно выбрать способ передачи версии, правила выбора версии по умолчанию, формат OpenAPI-документов, период поддержки, способ уведомления клиентов и integration-тесты для каждой поддерживаемой версии.
