# План разработки и обучения SupportFlow

## Назначение плана

Этот roadmap одновременно описывает развитие продукта и учебный маршрут. Его цель — не собрать как можно больше библиотек, а последовательно пройти полный цикл разработки production-like web-приложения: от бизнес-требования и HTTP-контракта до хранения данных, безопасности, тестирования, наблюдаемости и развёртывания.

План фиксирует направление, но не является неизменным техническим заданием. Перед каждым крупным этапом требования и выбранные решения уточняются. Если решение существенно влияет на архитектуру, для него создаётся ADR.

## Как мы будем работать

Каждая функция разрабатывается небольшим вертикальным срезом:

1. Формулируем пользовательский сценарий и критерии приёмки.
2. Проектируем HTTP-контракт и возможные ошибки.
3. Определяем бизнес-правила и границы транзакции.
4. Реализуем доменную модель, endpoint и работу с данными.
5. Добавляем модульные и интеграционные тесты.
6. Проверяем негативные сценарии, безопасность и наблюдаемость.
7. Обновляем документацию и проводим review через pull request.

Такой порядок даёт законченную функцию, проходящую через все слои приложения. Он также позволяет обсуждать архитектуру на конкретном сценарии, а не создавать абстракции заранее.

### Формат обучения

Для каждой новой темы мы будем разбирать:

- какую проблему решаем;
- как решение работает внутри;
- почему оно подходит SupportFlow;
- какие существуют альтернативы;
- какие у выбранного подхода ограничения и компромиссы;
- как проверить реализацию;
- как объяснить решение на собеседовании.

Production-код по возможности пишет автор проекта. Ревью должно указывать не только на ошибку, но и на нарушенное правило, возможные последствия и способ самостоятельно проверить исправление. Тесты можно разрабатывать совместно: сначала определять сценарии, затем писать реализацию и разбирать устройство теста.

## Возможные этапы после MVP

Эти функции полезны для обучения, но не должны задерживать завершение основного продукта:

- загрузка вложений в S3-совместимое object storage с проверкой типа и размера;
- real-time обновления через SignalR;
- полнотекстовый поиск PostgreSQL, а затем сравнение с отдельным search engine;
- Redis для подтверждённого сценария распределённого кэша;
- внешний OpenID Connect provider;
- импорт обращений из электронной почты;
- feature flags;
- локализация;
- извлечение одного модуля в отдельный сервис как учебный эксперимент;
- message broker и обработка интеграционных событий между процессами.

Добавлять эти технологии заранее не следует: иначе появится инфраструктурная сложность без пользовательской ценности и без возможности сравнить решение с более простым вариантом.

## Что мы намеренно не добавляем заранее

- Generic Repository поверх EF Core — `DbContext` уже предоставляет Unit of Work и похожий на Repository интерфейс. Собственная абстракция появится только при конкретной пользе, а не ради названия паттерна.
- MediatR или другой mediator — сначала поток выполнения остаётся явным. Библиотеку оценим, когда появятся повторяющиеся pipeline behaviors или достаточное количество команд и обработчиков.
- AutoMapper — ручное преобразование небольших контрактов проще читать и проверять. Автоматический mapping рассмотрим при большом объёме действительно механического кода.
- Redis — кэш добавляется после измерения производительности и определения правил инвалидирования.
- Message broker — для одного процесса сначала достаточно прямого вызова или локальной фоновой обработки. Broker имеет смысл при разделении процессов и требованиях к доставке.
- Микросервисы и Kubernetes — до появления требований к независимому развёртыванию и масштабированию они увеличат стоимость разработки и эксплуатации без пользы для MVP.

Это не запрет на технологии. Это практика архитектурной целесообразности: сначала должна появиться проблема, затем критерии выбора и только после этого инструмент.

## Общий Definition of Done для функции

Функция считается завершённой, когда:

- сформулированы пользовательский сценарий и критерии приёмки;
- HTTP-контракт содержит корректные успешные и ошибочные ответы;
- бизнес-инварианты нельзя обойти через другой вход в систему;
- проверены аутентификация, авторизация и границы организации, если они применимы;
- изменение схемы оформлено миграцией и имеет необходимые ограничения и индексы;
- код не нарушает направления зависимостей модулей;
- добавлены тесты подходящего уровня;
- проверены логи и отсутствие утечки чувствительных данных;
- сборка и тесты проходят локально и в CI;
- документация обновлена в том же pull request;
- pull request прошёл review и замечания устранены;
- автор может объяснить решение, его альтернативы и компромиссы.

## Как отслеживать прогресс

Этот файл хранит крупные этапы и учебные цели. Текущий этап помечается `[>]`, завершённые пункты — `[x]`. Детальные задачи конкретной функции ведутся в pull request или GitHub Issues, чтобы roadmap не превращался в журнал каждого изменения.

После завершения этапа мы:

1. Обновляем его статус.
2. Фиксируем полученные навыки и важные решения.
3. Проводим короткую ретроспективу: что получилось, что было сложно и что стоит улучшить.
4. Формулируем несколько вопросов для самопроверки перед собеседованием.
5. Уточняем следующий этап на основании уже работающей системы.

## Ориентировочный темп

При занятиях по 3–4 часа после работы разумно планировать не даты, а небольшие законченные итерации. Одна итерация обычно занимает от нескольких занятий до двух недель и завершается работающим сценарием, тестами, документацией и pull request.

Сроки не являются критерием успеха. Важнее не копировать код механически, а уметь объяснить поток запроса, границы ответственности, SQL, тестовую стратегию, угрозы безопасности и эксплуатационные последствия решения.
